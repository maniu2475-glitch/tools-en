What a CRC actually checks

CRC stands for Cyclic Redundancy Check. The algorithm treats the input bits as one long polynomial and divides them by a fixed generator polynomial, keeping only the remainder as the checksum. CRC-32 as used here applies the reflected IEEE 802.3 polynomial 0xEDB88320, starts from 0xFFFFFFFF and XORs the final result, which is the variant behind ZIP, PNG, Ethernet frames and gzip. Because the maths is polynomial division over GF(2), any single-bit error is guaranteed to be caught, as is any burst error up to 32 bits long. For a random corruption the chance of an undetected error is roughly one in four billion.

CRC-32 versus cryptographic hashes

A CRC is built to catch accidents, not attacks. It is linear, so an attacker can craft arbitrary changes that keep the same checksum — it is trivially easy to fabricate a collision. MD5 and SHA-256 are designed to resist that: they are non-linear, and SHA-256 has no known practical collisions. The practical rule is CRC-32 for speed on files and network frames, and a cryptographic hash when integrity must be defended against a malicious party. That is why this page shows all three at once: CRC-32 tells you quickly whether a download is intact, while SHA-256 lets you compare against a published release file.

Where you will meet CRC-32

Every entry in a ZIP central directory stores a CRC-32 so archivers can spot truncation. PNG chunks each carry a CRC-32 over their type and data, which is why a corrupted PNG often fails to decode rather than showing garbage pixels. Ethernet frames, Bluetooth packets and many ROM formats use it as well. Web tools often show it in uppercase hex without the 0x prefix, so the value here is displayed in both styles — compare only the eight digits. For a faster modern alternative, the SHA-256 generator gives a cryptographic digest; for quick text integrity checks the MD5 generator is also available.
