Counting lines sounds trivial until you try it

Every operating system disagrees about what ends a line. Unix uses a single line feed (\n, 0x0A), classic Mac OS used a single carriage return (\r, 0x0D), and Windows uses both in sequence (\r\n). A file written on Windows and read by a naive Unix counter will still have the carriage returns embedded in it, and a file whose final line has no terminator is famously miscounted by command-line tools like wc -l, which counts newline characters rather than lines and therefore reports one fewer than humans expect. This counter splits on any of the three conventions, so pasted text from any source gives the number you would get by scrolling to the bottom of a text editor.

Blank lines are the hidden variable

Source code files are typically 15 to 25 percent blank lines, and that proportion matters for enforcements like "no function may exceed 100 lines" or for pricing a translation job. The ignore-blank-lines checkbox flips the main figure between raw line count and meaningful line count, while the second row always reports both so you can compare. A line containing only spaces or a tab is treated as blank, because visually it is.

Characters, words and bytes

The character count with spaces is what word-processor limit dialogs mean, and the count without spaces is what Twitter-style length checks effectively use. Byte size is different again: it is the UTF-8 encoded length, so an emoji or an accented letter occupies more than one byte even though it is a single character. Longest line and average line length are useful signals when you are deciding how to wrap a Markdown table, a commit message or a CSV column that a tool refuses to read. If you only need a word count, the word counter is a lighter page; for a full breakdown including reading time, use the reading time calculator.
